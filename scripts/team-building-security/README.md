## Manual names create labels, not accounts

`cloud.addMember(name)` creates only a label inside this owner's private journal directory. The named person receives no login, account, role, access grant, profile or notification. No global workbook directory or authentication data is written.

Names are normalized with NFKC, whitespace collapse and trim. A label has 1–40 Hangul/ASCII letter/digit characters with internal single spaces, underscores or hyphens. The normalized lowercase name is its uniqueness key. The UI escapes labels as text.

The adapter atomically writes:

- `members/custom_{32 hex}`: name, fixed role `IC`, active true, actual createdBy and current createdAt.
- `nameIndex/{lowercase name}`: the member ID.

Rules require both directions to agree in the new atomic snapshot. Owner writes can only create missing custom members and missing index entries; canonical members, existing labels, index values, directory metadata, configuration and reports cannot be overwritten or deleted. Partial writes, forged actor/role/stamp, unknown fields and other-owner paths are rejected.

The initial index includes canonical labels, preventing duplicate registration of an existing teammate. Concurrent duplicate submissions converge to the same stored member; duplicate lookup reuses the existing active member. Inactive names remain reserved for history and require an administrator to resolve.

The additive migration creates only `memberIndexVersion` and `nameIndex`. It preserves every canonical/custom member, daily record, report and unrelated feature field. No demonstration labels or records are created in production.

## Daily records and analytics

Documents enforce exact owner, actual calendar date, schema version, advancing integer revision, actual writer and recent timestamp. Parent validation covers every descendant write, preventing a partial-write revision bypass. Unknown fields, malformed dates, negative/fractional/oversize counts, oversize text and fake teammates are denied.

Donor and Close quantities are separate. Null means unrecorded; explicit zero remains zero. Goal comparisons use confirmed donor goals and donor actuals. Care percentages exclude “not applicable.”

Care answers and teammate sales are keyed maps in the database, preventing duplicate IDs, while the adapter returns UI arrays. New entries require current directory identity. Historical rows retain their original name after rename/departure. Whole-day deletion is denied; clearing values requires an advancing revision.

Analytics is descriptive aggregation generated by the authenticated administrator and saved only in the protected aggregate node, with source revisions and generation time. Refresh after a later daily edit. The owner necessarily can reason about their readable raw records; permissions protect the application's analytics view, collection endpoint and saved reports.

The adapter rechecks identity before/after requests, rejects offline saves and clears its subscriptions/memory on revocation. Disposed-account responses cannot repopulate the previous account. A timed-out write may have reached the server; revision conflicts protect retry from silent overwrite.

## Publication

Normal Firebase CLI authentication is established. Scripts reuse only that session; they never initiate OAuth, request extra scopes or expose tokens.

For an initial installation, `deploy.cjs` separately prepares and applies a new node. It refuses existing feature data.

For the manual-name extension:

1. Run `update-manual-members.cjs --prepare --deployment-auth-approved --output=/private/tmp/<review>`.
2. Review private backup, exact rules delta, additive directory patch and hashes. Run all emulator checks against that `before.json`.
3. Root approves the exact merged hash. Within five minutes, run `--apply --approved --deployment-auth-approved --review-dir=<review> --approved-merged-sha=<hash>`.
4. A missing rules ETag requires an explicit root decision to add `--allow-no-etag`. Two immediate rule comparisons and exact post-read hashes remain mandatory. Directory migration requires a fresh data ETag and conditional PUT of the exact prior directory plus the reviewed additive fields.
5. Readback must prove all original members, daily records and analytics unchanged. Preserve `publication-proof.json`. Never blindly retry a partial publication.
6. Publish the frontend, then verify authenticated default-view read and production non-authenticated denials without fabricating real journal records.

Private review snapshots contain real data and must not be committed or exposed in public artifacts. Public proof should contain only policy hashes, counts and preservation booleans.

The first migration attempt used conditional PATCH, which returned HTTP 400 after the reviewed rules update. Read-only verification proved all feature data unchanged. A separately reviewed conditional PUT completed the two-field migration and verified all original members, daily records and analytics preserved. No sample label or daily record was written. [Firebase's REST documentation](https://firebase.google.com/docs/database/rest/save-data#updating_data_with_conditional_requests) specifies conditional PUT/DELETE; the script now uses PUT and has an explicitly reviewed, hash-bound `--recover` branch for this partial state.
